# Free public demo: Vercel (website) + Render (backend)

This deploys LocalStock at no cost using free tiers:

| Piece | Host | Free plan |
| --- | --- | --- |
| Website (React/Vite) | Vercel | Hobby |
| API + worker (one process) | Render web service | Free |
| Redis | Render Key Value | Free |
| PostgreSQL + PostGIS | Neon | Free |
| RabbitMQ | CloudAMQP | Little Lemur |

The site is a **demo**: it is seeded with sample sellers and products, shows a demo notice, and
"pays" through the sandbox. No external platform prices are fetched. Platform links only open the
platform's own search page in the shopper's browser.

## Limits of the free tiers

- **Render sleeps the backend after 15 minutes without traffic.** The next visit then takes about a
  minute while it starts. The worker sleeps with it: reservations expire and outbox events are
  published only while the backend is awake. That is fine for a demo but not for real orders.
  An external pinger keeps it awake during the day: see [Keep the backend awake](#keep-the-backend-awake-cron-joborg).
  It stays off the rest of the day because the worker queries the database every second while
  awake, and running all day would use about 186 of Neon's 100 free compute-hours a month.
- The Render free plan has no background workers and no pre-deploy commands, so
  `deploy/all-in-one.mjs` runs migrations, the API and the worker in one process
  (`deploy/render/Dockerfile`). Elsewhere, run them as separate services.
- Render's free Key Value is in-memory only. Losing it costs only cache and rate-limit counters.
- The Neon free tier caps storage and compute hours, and CloudAMQP Little Lemur caps connections
  and messages. A demo stays well inside both.

## 1. Merge to `main`

`render.yaml` deploys the `main` branch. Merge `feature/unified-external-platform-discovery` into
`main` on GitHub, or locally run `gh auth login` and open and merge the pull request.

## 2. Neon: PostgreSQL with PostGIS

1. Sign up at <https://neon.tech> and create a project (pick the region closest to your Render
   region, e.g. AWS Singapore for India).
2. On **Connection details**, turn **Connection pooling off**. Migrations take an advisory lock,
   which needs a direct connection.
3. Copy the connection string. It looks like
   `postgresql://user:password@ep-xxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.

You don't need to do anything else: the first migration creates the `postgis`, `pg_trgm` and
`pgcrypto` extensions, and Neon supports all three.

## 3. CloudAMQP: RabbitMQ

1. Sign up at <https://www.cloudamqp.com> and create an instance on the free **Little Lemur** plan,
   in the same region as the other services.
2. Open the instance and copy the **AMQP URL** (`amqps://user:password@xxx.rmq.cloudamqp.com/vhost`).

## 4. Render: backend and Redis

1. Sign up at <https://render.com> with GitHub and give it access to the repository.
2. **New → Blueprint**, pick the repository and branch `main`. Render reads `render.yaml` and
   offers to create `localstock-api` (web service) and `localstock-redis` (Key Value).
3. Fill in the values it asks for:
   - `DATABASE_URL`: the Neon string from step 2.
   - `RABBITMQ_URL`: the CloudAMQP URL from step 3.
   - `SEED_PASSWORD`: the password every demo account gets. It must be at least 16 characters and
     not the public default. Keep it private; it signs in as the demo admin.
   - `JWT_ACCESS_SECRET` and `PAYMENT_WEBHOOK_SECRET` are generated by Render.
4. Click **Apply**. The first deploy builds the image, runs migrations, seeds the demo data and
   starts the API. Watch the logs for `worker started`.
5. Open `https://localstock-api.onrender.com/health/ready` (your service URL may have a suffix,
   e.g. `localstock-api-ab12.onrender.com`). It should report Postgres and Redis as up.

## 5. Vercel: website

1. If Render gave the service a different URL from `localstock-api.onrender.com`, replace it in
   both rewrites in `apps/web/vercel.json`, then commit and push.
2. Sign up at <https://vercel.com> with GitHub, **Add New → Project**, import the repository.
3. Set **Root Directory** to `apps/web`. Vercel detects Vite. Keep the build command
   (`npm run build`) and output directory (`dist`).
4. Add the environment variable `VITE_DEMO_NOTICE` = `on` so the site says it is a demo.
5. **Deploy**, then open the `*.vercel.app` URL.
6. Optional: in the project, open **Analytics → Enable** (Web Analytics, free on Hobby). The site
   already includes `@vercel/analytics`; page views appear after the next visit. Order and company
   ids and search terms are removed from URLs before they are sent (`apps/web/src/lib/url-privacy.js`).
7. Optional: **Speed Insights → Enable** (free on Hobby, with a monthly data-point limit). The site
   already includes `@vercel/speed-insights` with the same URL filter.

The website calls `/api/...` and `/health/...` on its own domain, and Vercel forwards them to Render
(`apps/web/vercel.json`). The browser therefore needs no CORS setup and never sees the Render URL.

## 6. Check the demo

- Sign in with a seeded account and the `SEED_PASSWORD` you chose: `customer@localstock.dev`,
  `seller.a@localstock.dev`, `seller.b@localstock.dev`, or `admin@localstock.dev` (platform admin).
- Search for a product, add it to the cart, check out and use the sandbox **Pay** button.
- In Admin, check the platform list. Every external source reads **Disabled**, which is expected:
  none has a verified, permitted data source configured.

## Keep the backend awake (cron-job.org)

The live website is **https://master-app-jm7g.vercel.app** (Vercel project `master-app-jm7g`). While the
backend sleeps, the header shows **Offline** for about a minute until Render has started it again.

The repository's `Keep demo awake` GitHub Actions workflow was meant to prevent that, but GitHub delays
and drops scheduled runs on free repositories: on 3 and 4 Nov 2026 it ran only twice a day instead of
about 54 times. Use [cron-job.org](https://cron-job.org) (free) instead:

1. Sign up at <https://cron-job.org> and confirm the email address.
2. **Create cronjob** with:
   - **Title:** `LocalStock keep awake`
   - **URL:** `https://localstock-api.onrender.com/health/live`
   - **Schedule:** custom; minutes every 10 (0, 10, 20, 30, 40, 50), hours 9 to 18, every day.
   - **Time zone:** `Asia/Kolkata`
   - Optional: email notification after several failures in a row.
3. Save, then **Test run**. A healthy backend answers `200` with `{"status":"ok"}`.

The backend is then awake from about 09:00 to 19:00 IST, which keeps Neon's compute-hours within the free
plan. Outside that window the first visitor waits about a minute. A ping that reaches a sleeping backend may
time out while it starts; that is expected, and the next ping succeeds. To change the hours, edit the
cronjob's schedule; keep the window short enough for Neon's free plan.

The GitHub workflow (`.github/workflows/keep-awake.yml`) is kept as a backup. It does no harm, and can be
switched off under **GitHub → Actions → Keep demo awake → ⋯ → Disable workflow**.

## Rate limits behind the proxies

`TRUST_PROXY=2` (set in `render.yaml`) makes the API take the visitor's address from
`X-Forwarded-For` written by Vercel and Render. Without it, every visitor would share one rate
limit. The trade-off: someone calling the Render URL directly can choose the address they are
limited under. For a demo that is acceptable. For production, put the API behind a single proxy you
control and set `TRUST_PROXY` to match.

## Updating

Pushes to `main` redeploy both: Render rebuilds the backend (migrations run again and are
idempotent; seeding skips existing data), and Vercel rebuilds the website.
